跨设备联机 — 架构方案

两个设备各玩各的 → 需要网络同步。NES 联机的核心问题是：怎么让两台设备的画面保持一致？

A

输入同步 — 双端各自运行

双方都加载同一个 ROM，只交换控制器输入。WebRTC P2P 直连，延迟极低。需要双方都有 ROM 文件。RetroArch 的经典方案。

B

画面串流 — 主机运行，客机投屏

主机一人运行模拟器，把画面+音频实时送到客机，客机只发回按键。类似 Stadia/云游戏模式，但实现更简单。

方案 A — 输入同步（推荐）

┌─────────────── 玩家 1 (主机) ───────────────┐
│  🎮 本地 P1 输入                             │
│  📡 接收 P2 输入 ←── WebRTC DataChannel ──┐ │
│  ⚙ 本地 WASM 模拟 (P1+P2 输入)            │ │
│  🖥 渲染画面 + 🔊 音频                      │ │
└─────────────────────────────────────────────┘ │
                                               │
┌─────────────── 玩家 2 (客机) ───────────────┤
│  🎮 本地 P2 输入                             │
│  📡 发送给主机 ─── WebRTC DataChannel ────┘ │
│  ⚙ 本地 WASM 模拟 (同样 P1+P2 输入)         │
│  🖥 渲染画面 + 🔊 音频                        │
└─────────────────────────────────────────────┘

🟢 优势：每帧仅传 ~2 bytes（手柄位），延迟 <10ms
🔴 风险：双方 ROM 必须完全一致；模拟器必须确定性运行

方案 B — 画面串流

┌───────── 玩家 1 (主机) ────────┐
│  🎮 本地 P1 输入                │
│  ⚙ 运行模拟器                   │
│  📹 Canvas.captureStream()     │
│  📡 视频流 → WebRTC VideoTrack  │
└─────────────────────────────────┘
              │
              ▼  WebRTC 视频 + 数据通道
┌───────── 玩家 2 (客机) ────────┐
│  📺 接收视频流，渲染到 Canvas    │
│  🎮 本地 P2 输入 → 发回主机     │
│  ⚙ 客机不运行模拟器             │
└─────────────────────────────────┘

🟢 优势：客机不需要 ROM；只保证主机模拟正确即可
🔴 风险：视频流带宽大（~1-5 Mbps），移动网络不友好

为什么推荐方案 A

  • 带宽极小：每帧 2 bytes，4G/弱 Wi-Fi 都能流畅
  • 延迟最低：不经过任何中转，P2P 直连
  • 架构一致：双方都走现有 Worker+WASM 管线，不额外引入视频编码
  • NES 天然适合：NES 是确定性系统，相同输入 = 完全相同状态

需要解决

  • 帧延迟缓冲（输入到达前暂缓几帧）抵消网络抖动
  • ROM 校验（双方启动前校验 ROM 的 SHA-256）
  • 连接建立需要信令服务器（轻量 WebSocket）

联机流程

Match Flow — 房间模式
1
主机点击"创建房间"
生成 4 位房间码，如 "AX3K"
2
客机输入房间码加入
通过信令服务器建立 WebRTC 连接
3
ROM 校验
双方 ROM 哈希比对，不匹配则主机自动发送 ROM 给客机
✓
同步启动 — 开始联机
主机 P1，客机 P2，帧级同步
